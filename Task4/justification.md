# Обоснование облачной инфраструктуры «Будущее 2.0»

## 1. Общая концепция

Для размещения инфраструктуры выбран Yandex Cloud,
регион ru-central1.

Инфраструктура предназначена для размещения базовых
компонентов платформы данных компании «Будущее 2.0».

Используется декларативный подход Infrastructure as Code
на базе Terraform.

Terraform управляет сетевыми ресурсами, виртуальными
машинами, дисками, NAT и группами безопасности.

## 2. Сетевая архитектура

Создаётся одна виртуальная сеть VPC с двумя подсетями:

- Public subnet: 192.168.10.0/24.
- Private subnet: 192.168.20.0/24.

Публичная подсеть используется для Bastion VM.
Приватная подсеть предназначена для размещения
внутренних компонентов платформы данных.

Разделение позволяет ограничить доступ к внутренним
сервисам и исключить их непосредственную публикацию
в интернете.

### NAT Gateway

Для приватной подсети используется управляемый
NAT Gateway Yandex Cloud.

Он обеспечивает исходящий доступ к интернету для
обновления ОС, загрузки пакетов и получения
обновлений программного обеспечения.

При этом приватные виртуальные машины не получают
публичные IP-адреса.

Для маршрутизации используется отдельная таблица
маршрутов со следующим правилом:

- Назначение: 0.0.0.0/0.
- Следующий узел: NAT Gateway.

Это позволяет централизовать исходящий трафик
и не открывать входящие подключения.

## 3. Виртуальные машины

### 3.1. Bastion VM

Назначение: административная точка входа
во внутреннюю инфраструктуру.

Параметры:

- 2 vCPU;
- 2 GB RAM;
- 20 GB SSD;
- Ubuntu 22.04 LTS;
- публичный IP.

Небольшой объём ресурсов достаточен, поскольку
виртуальная машина не выполняет вычислительные
задачи платформы.

Доступ по SSH разрешён только с IP-адреса
администратора.

### 3.2. Data Platform VM

Назначение: размещение компонентов платформы данных
и выполнение учебных нагрузок.

Параметры:

- 4 vCPU;
- 8 GB RAM;
- 30 GB системный диск;
- 100 GB дополнительный SSD;
- Ubuntu 22.04 LTS;
- только приватный IP.

Ресурсы выбраны как начальная конфигурация
для учебного MVP.

4 vCPU позволяют выполнять несколько параллельных
задач обработки данных.

8 GB RAM достаточно для базового набора
небольших сервисов, тестирования ETL и SQL-запросов.

Для промышленного развёртывания Kafka, Trino,
Airflow и Lakehouse потребуется отдельное
планирование ресурсов и распределение нагрузки
между несколькими узлами.

### 3.3. Диски

Используются отдельные диски:

- Boot Disk — 30 GB.
- Data Disk — 100 GB.

Разделение позволяет независимо управлять
системными и рабочими данными.

При переустановке операционной системы
дополнительный диск может быть сохранён
и подключён повторно.

Для дисков выбран тип network-ssd,
обеспечивающий более высокую производительность
по сравнению с обычным HDD.

## 4. Безопасность

Для ограничения сетевого доступа используются
Security Groups.

Bastion VM:
- входящий SSH только с IP администратора;
- исходящие подключения разрешены.

Data Platform VM:
- входящий SSH только из публичной подсети;
- публичный IP отсутствует;
- исходящий трафик проходит через NAT.

SSH-аутентификация выполняется по ключам.
Парольная аутентификация не используется.

В промышленной эксплуатации дополнительно
потребуются:
- централизованное управление секретами;
- журналирование административного доступа;
- резервное копирование;
- мониторинг сетевых событий;
- ограничение исходящего трафика по назначениям.

## 5. Декларативный подход Terraform

Terraform описывает желаемое состояние инфраструктуры,
а не последовательность ручных операций.

Основные преимущества:

1. Воспроизводимость.
   Одинаковая конфигурация позволяет создавать
   одинаковую инфраструктуру в разных окружениях.

2. Контроль изменений.
   Команда terraform plan показывает предполагаемые
   изменения до их применения.

3. Управление зависимостями.
   Terraform самостоятельно определяет порядок
   создания взаимосвязанных ресурсов.

4. Масштабируемость.
   Параметры виртуальных машин, дисков и сетей
   вынесены в переменные.

5. Версионирование.
   Конфигурация может храниться в Git и проходить
   code review.

6. Снижение количества ошибок.
   Исключается необходимость повторять большое
   количество ручных операций.

## 6. Развитие инфраструктуры

Предложенная конфигурация является первым этапом
создания облачной платформы.

В дальнейшем возможно:

- добавление отдельных VM для Kafka и Airflow;
- выделение Trino в отдельный вычислительный контур;
- переход к Managed Service;
- использование Object Storage для Lakehouse;
- создание нескольких зон доступности;
- настройка резервного копирования;
- внедрение централизованного мониторинга;
- автоматическое развёртывание приложений через Ansible.

Terraform позволит добавлять ресурсы без
необходимости полностью пересоздавать инфраструктуру.

## 7. Ограничения текущего решения

Текущая конфигурация предназначена для учебного
и пилотного окружения.

Она не обеспечивает полноценную промышленную
отказоустойчивость:

- используется одна зона доступности;
- отсутствует резервная VM платформы;
- не настроен geo-DR;
- не реализовано автоматическое резервное
  копирование дисков;
- NAT и Bastion являются общими компонентами
  инфраструктуры.

Перед промышленным использованием необходимо
разработать отдельную архитектуру отказоустойчивости
и определить RTO/RPO.

## 8. Вывод

Предложенная архитектура обеспечивает безопасную
сетевую основу для развития платформы данных
«Будущее 2.0».

Использование Terraform позволяет воспроизводить
инфраструктуру, контролировать изменения и
масштабировать ресурсы по мере подключения
новых бизнес-направлений.
