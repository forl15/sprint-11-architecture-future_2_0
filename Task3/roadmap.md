# Роадмап изменений «Будущее 2.0»

**Горизонт:** 12 месяцев + поэтапный вывод легаси (волна 3; полный вывод может выйти за 12 месяцев).
**Три обязательные оси:** портал самообслуживания; независимость подразделений; качество мед/фин-сервисов.
**Архитектурный принцип:** бизнес-логика принадлежит доменам; платформа обеспечивает интеграцию, хранение, обработку и выдачу данных и не становится новым хранилищем бизнес-правил.

Технологический выбор описан в [технологическом радаре](technology-radar.md).

## Волны

| | Срок | Тема | Ключевой результат |
|---|---|---|---|
| 0 | 0–2 мес | Фундамент и Governance (гейт) | Правила, домены, доступ и MVP согласованы; 0 нарушений |
| 1 | 2–6 мес | MVP платформы и портала | Первые домены и отчёты; 90% отчётов — менее 5 мин |
| 2 | 6–12 мес | Независимость и self-service | ≥ 80% запросов без ИТ; KPI едины; пилот партнёра |
| 3 | 12+ мес | Поэтапный вывод легаси | Легаси вне критического пути; TCO ниже |

## Волна 0 · 0–2 мес — Фундамент и Governance (гейт)

**Цель:** договориться о правилах до промышленной загрузки данных.

| Направление | Результат |
|---|---|
| Портал | Сценарии, каталог, конструктор; согласованный MVP и backlog |
| Домены | 6 доменов, владельцы, допустимые для аналитики данные |
| Интеграция | Шаблоны Data Contract и API; единые правила обмена |
| Безопасность | Классификация, ABAC, модель угроз, аудит; security baseline |
| Инфраструктура | Landing zone с изолированными средами dev/test/prod |

**Решения:** Keycloak (SSO/MFA), OPA (политики доступа), Data Contracts, изолированные среды. Мораторий на новую логику в DWH; медкарты и исследования вне аналитики.

**Гейт:** 0 нарушений политик мед/фин-данных — загрузка разрешена.
**Команды и ресурсы:** PMO, архитектор, CISO, Platform Team, владельцы доменов; 1–2 инженера платформы, ИБ, аналитик, Product Owner.

## Волна 1 · 2–6 мес — MVP платформы и портала

**Цель:** запустить MVP (пилотный контур, а не вся платформа), подключить первые домены и дать бизнесу первые отчёты.

| Компонент | Технология |
|---|---|
| Приём событий, CDC, API | Kafka, Debezium, API Gateway |
| Хранение | S3 + Iceberg (lakehouse) |
| Обработка и трансформации | Airflow, dbt |
| SQL-доступ | Trino |
| Каталог | OpenMetadata |

**Хранение:** Raw (исходные) → Curated (проверенные) → Gold (готовые витрины и Data Products).

**Первые домены:** финтех и корпоративный. Поток: `Финтех → Kafka/API/CDC → проверка контракта → Raw → Curated → Gold → семантика`. Бизнес-правила платежей и кредитования остаются в финтех-системах. Клиника, ИИ, партнёры и оборудование — в волне 2; медкарты и исследования в аналитику не поступают.

**Портал MVP:**
- вход через Keycloak, каталог и поиск;
- доступ по цели через OPA, аудит действий;
- 10–20 типовых отчётов;
- временно — существующие отчёты Power BI.

**Безопасность:** проверка схем и контрактов, карантин брака, изоляция мед- и фин-контуров, маскирование, аудит.

**Результат:** 90% отчётов — менее 5 мин; новый домен — 4–6 недель; Data Products без изменения логики DWH; 0 медкарт.
**Команды и ресурсы:** Platform/Data Engineering, финтех, корпоративный ИТ, Portal Team, IAM/Security, BI; боевое облако, 2–3 BI-инженера, 20–30% времени доменных команд.
**Критерий:** пользователь находит отчёт и получает его в соответствии со своими полномочиями.

## Волна 2 · 6–12 мес — Независимость и self-service

**Цель:** перейти от пилота к промышленной эксплуатации и самостоятельной работе подразделений.

**Портал:** конструктор (измерения, фильтры, группировки, сохранённые представления), подписки, экспорт с проверкой прав; работа через семантический слой без произвольного SQL; перевод 30–50 отчётов; ≥ 80% запросов без ИТ; нагрузочное тестирование.

**Домены (Data Mesh, Trial в радаре):**

| Домен | Реализация |
|---|---|
| Клинический | Разрешённые агрегаты без медкарт и исследований |
| ИИ | Метрики моделей; медданные не покидают контур |
| Финтех | Data Products по платежам и кредитам |
| Корпоративный | Единые KPI головного офиса |
| Партнёрский | Пилот фармы по типовым контрактам |
| Оборудование | Телеметрия, события, сервисные показатели |

**Партнёры:** `API → проверка контракта → классификация → Raw → Curated → Gold → каталог`; в волне 2 — шаблоны и пилот, масштабирование — в волне 3.

**Семантика (Cube):** единые KPI и измерения, доступ на уровне моделей, предагрегация, API для портала и BI.

**Качество:** RLS/CLS в семантическом и SQL-слоях; DQ при публикации; lineage; мониторинг свежести и полноты; backup/restore; multi-AZ и geo-DR; Prometheus/Grafana/Loki; SLA/RTO/RPO по классам.

**Результат:** портал в промышленной эксплуатации; ≥ 80% self-service; 30–50 отчётов; KPI едины; пилот партнёра; SLA 99,9% / 99,95% по классам.
**Команды и ресурсы:** Portal Team, BI, доменные команды, Data Governance, Security, SRE, FinOps; пиковый облачный бюджет, SRE, время BI на перевод отчётов.
**Критерий:** ≥ 80% запросов без ИТ; 30–50 отчётов переведены.

## Волна 3 · 12+ мес — Поэтапный вывод легаси

**Цель:** убрать зависимость от устаревших систем после переноса их функций.

| Система | Замена |
|---|---|
| SQL Server 2008 | Доменная логика — в сервисы, аналитика — в dbt/ETL |
| PowerBuilder | Операторские интерфейсы — в доменные приложения |
| Apache Camel | Интеграции — в Kafka и API Gateway |
| Power BI | Сертифицированные модели и портал |

**Strangler:** инвентаризация → реализация функции → параллельная эксплуатация → сверка результатов → переключение → отключение после согласования.

Полная замена легаси **не является условием** запуска портала через год; вывод может занять больше 12 месяцев, старые и новые контуры работают параллельно. Партнёры масштабируются по шаблону волны 2: 4–6 недель.

**Результат:** TCO ниже за счёт поэтапного вывода EOL-платформ; легаси вне критического пути.
**Команды и ресурсы:** legacy-группа, SRE, доменные команды; параллельная работа контуров, бюджет на сверку данных.

## SLA, RTO и RPO по классам

Единое требование SLA ко всем системам не применяется. **99,95% для критичных компонентов — ориентир, подтверждаемый после анализа стоимости**; портал начинается с 99,9%.

| Класс системы | Примеры | SLA | RTO | RPO |
|---|---|---|---|---|
| Критичные клинические сервисы | запись, результаты, назначения | 99,95% (после анализа стоимости) | 1 ч | 15 мин |
| Платёжный / финансовый контур | платежи, карточные операции | 99,95% | 1 ч | 5 мин |
| Портал самообслуживания | каталог, отчёты, подписки | 99,9% — стартовая цель | 8 ч | 1 ч |
| Аналитика и витрины (некритичные) | BI, исследования, отчётность HQ | 99,5% | 24 ч | 24 ч |

99,95% ≈ 4,4 ч простоя в год, 99,9% ≈ 8,8 ч, 99,5% ≈ 43,8 ч. Для платежей RPO 5 мин строже, чем для медданных. Значения согласуются с бизнесом, CISO и регуляторами; нагрузочное тестирование и restore drill — условие промышленной эксплуатации.

## Архитектурные зависимости

1. Домены и владельцы — до разработки контрактов.
2. Классификация данных — до загрузки в аналитику.
3. Платформа приёма — до формирования lakehouse.
4. Data Products — до полноценного self-service.
5. IAM и политики доступа — до доступа бизнеса.
6. DQ, аудит, резервирование и нагрузочные тесты — до промышленной эксплуатации.

## Бизнес-обоснование

**Скорость решений (S1–S2):** единые KPI и витрины дают 90% отчётов менее 5 минут вместо часов; ≥ 80% запросов бизнес закрывает сам через портал.

**Скорость вывода продуктов (S5):** доменные контракты и стандартная интеграция — 4–6 недель на новый домен или партнёра вместо месяцев через ESB и доработку DWH; пилот партнёра уже в волне 2.

**Качество мед/фин-сервисов (Q):** изоляция контуров, ABAC, маскирование и аудит до загрузки; 0 медкарт; DQ и единая семантика; SLA/RTO/RPO по классам; lineage и аудит доступа; PCI DSS для финтеха.

**Затраты:** поэтапный вывод EOL-систем и ESB снижает TCO без big-bang; split-бюджет по доменам и tiering хранения делают стоимость прозрачной; контракты переводят новые подключения в шаблон.

**Масштабирование:** lakehouse и события принимают новые домены без перестройки; хранение и вычисления масштабируются независимо; Data Governance убирает организационное узкое место.

**Главный результат:** к концу года — работающий портал самообслуживания и независимая платформа данных; миграция легаси становится управляемой последовательностью проектов.

## Риски и принципы

- **Strangler:** вывод по мере переноса функций; старые отчёты работают до перевода; возможен выход за 12 месяцев.
- **Гейты волн:** загрузка — после гейта волны 0; вывод легаси — после переноса зависимостей и проверки.
- **Критичные сервисы вне миграции:** мед- и платёжный контуры не затрагиваются переносом аналитики.
- **SLA по классам:** единый SLA не применяется; цели подтверждаются анализом стоимости.
- **Бизнес-логика в доменах:** платформа не становится хранилищем бизнес-правил.
- **Легаси не блокирует портал:** запуск через год не зависит от сроков отключения старых систем.
